docs-site: resúmenes de PR sin iframe, con UI SDK y legibles por un agente

Before, los resúmenes de PR de summarize-pr (prs/55 y prs/59) se veían en el sitio dentro de un iframe: raro en el teléfono (bandas arriba y abajo), y un agente desde la página no ve lo de adentro.

Now, prs/<n>.md sale de prs/<n>.html con un conversor: Markdown con marcas as cuyos componentes usan UI SDK, con el tema del sitio y sin iframe. El HTML queda como “Ver el original”.

La página como servidor MCP sirve para cualquier página del sitio, no solo PRs: cualquier doc de DocsifyTemplate pasa a ser algo que un agente lee y usa con 4 herramientas, sin DOM. El eval de prompt-bench (examples/docsify-pr-agente, en un PR aparte de prompt-bench) mide eso: Haiku 5.5 con solo esas 4 herramientas contestó 5 de 5 preguntas sobre #59.

Cierra #62. Nadie lo probó en Firefox ni en Safari (solo en Chromium headless). Nadie probó una tabla de tests escrita a mano; un bloque libre, solo en el fixture.

Flujo

Un resumen en el sitio

El resumen de #59, antes y ahora. Cada bloque de la página de summarize-pr es una marca as; el código, los gráficos y los comentarios van en bloques de código tal cual. En GitHub se lee como un documento.

Conversor y validador

El motor (pr/) es puro: lee el HTML como datos, escribe el Markdown y cuenta lo que tienen los dos. bin/pr.mjs es el transporte. Antes de escribir, corre el chequeo de summarize-pr sobre el HTML; después, compara el Markdown contra el HTML: los mismos bloques, cada texto y cada dato byte a byte (código de cada diff, DOT, tooltips, links, comentarios).

El conversor toma una lista cerrada: los bloques de la plantilla y los bloque libres. Un bloque que se parece a uno de la plantilla y no lo es lo hace fallar; el conversor nunca adivina.

Componentes con UI SDK

Decision Los avatares salen de GitHub y las etiquetas de la plantilla quedan en inglés Implicit

Los avatares de los comentarios salen de github.com/<login>.png en vez de data URIs. Las etiquetas de la plantilla (Before/Now, Why, Trade-off, Decision, Implicit) quedan en inglés, igual que en el HTML.

Trade-offUna página en español muestra esas etiquetas en inglés, y el lector carga cada avatar desde GitHub.

Un componente por bloque de la plantilla, en components/pr/, con la misma forma que los otros componentes del sitio. UI SDK va por dentro: read no lo conoce, y check.mjs sigue corriendo todo en Node; solo view dibuja ui-accordion, ui-collapsible, ui-segmented-control y ui-hover-card. El diseño visual está en pr.css y en 4 tokens nuevos de tokens.css.

El agente de la página

Decision La prosa le llega al agente con una herramienta read propia, al lado de las 3 de UI SDK Implicit

read devuelve el Markdown de la página por sección y los términos con su definición. El snapshot de UI SDK solo trae el título y la descripción de cada componente y salta lo oculto: ni con la decisión abierta trae el “por qué”. definePrimitive de UI SDK obligaba a reescribir el acordeón.

Trade-offEl sitio mantiene una herramienta fuera de UI SDK. Para revertirlo, se saca pageText/read de plugins/ui-sdk.js.

Decision window.agent es el agente de UI SDK sin tocar, y read va aparte, en window.pageText Implicit

El objeto de la librería queda como UI SDK lo hizo. Con WebMCP, la página registra read con la misma forma que registerTools de UI SDK.

Trade-offUn agente que maneja el navegador busca las cuatro herramientas en dos objetos. Para revertirlo, se cambian los nombres en plugins/ui-sdk.js.

Decision allow deja pasar todo lo que pide el agente Implicit

Una página de docs no tiene acciones que borren nada: el agente solo abre, cierra y cambia vistas.

Trade-offEl agente no le pregunta al lector antes de actuar. Un sitio que lo quiera pasa su propio allow.

Una sola copia de @ui-sdk/core: con dos, el snapshot del agente sale vacío.

Discarded idea

El ?bundle de esm.sh no ayuda: 116 requests contra 119, y más KB (prototipo). Queda ?deps=@ui-sdk/core@<versión> en el import map, que fija una sola copia de core.

La página como servidor MCP

Para un agente de afuera, la página es un servidor MCP con esas cuatro herramientas y ninguna más. El agente no ve el DOM ni corre código.

CI y deploy

Decision El job build corre en ubuntu-24.04 y no en ubuntu-latest (26.04) Implicit

Playwright todavía no trae Chromium para 26.04.

Trade-offEl job queda fijo en una versión vieja de Ubuntu. Para revertirlo, se vuelve a ubuntu-latest cuando Playwright traiga Chromium para 26.04.

En Chromium, test/pr_agente.py prueba A (una sola copia de core), B (el agente ve lo mismo que el HTML), C (abre decisiones, cambia a unified, muestra código oculto), D (lee la prosa con read) y un chequeo por cada “The template shows…” de summarize-pr. WebMCP lo prueba con un navegador falso (registra las 4 herramientas y read contesta); con uno real, no.

Decision La imagen de deploy sirve pr/summarize-pr/shown-lines.mjs Implicit

Los diffs de un resumen lo importan en el navegador para contar las líneas mostradas como lo cuenta summarize-pr.

Trade-offUn archivo de pr/, que es el motor de Node, también va en la imagen del sitio. Fuera de este diff, el skill pr-corto (MyClaudeSkills, ya en main) ahora dice que, si el repo tiene npm run docs:pr, el HTML pasa por el conversor.
