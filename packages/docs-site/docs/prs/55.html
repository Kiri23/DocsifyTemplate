docs-export: transporte browser (wasm externo) y plugin exportButton para Docsify 5

Before, exportar una página de Docsify a Typst (.typ) o PDF solo se podía desde la terminal (npm run docs:exportar).

Now, un botón en el sitio con Descargar .typ y Descargar .pdf arma el archivo en el navegador, sin servidor. El .typ es texto que un agente puede leer y editar; el PDF es para personas, con la plantilla de marca (branded.typ).

El botón es un plugin común de Docsify y no depende de site.js: cualquier sitio Docsify puede ofrecer su documentación en PDF con la plantilla de marca a alguien sin acceso al repo. El motor de exportación que ya corría en Node ahora corre en el navegador: solo cambian los engines que recibe.

Nadie probó el botón en Firefox (solo en Chromium). Cierra #50.

Cómo lo prende un sitio

El plugin no viene prendido. Con site.js, el sitio nombra un módulo suyo en pluginModules:

Sin site.js, el sitio suma el mismo exportButton(…) a window.$docsify.plugins desde un <script type="module"> antes del <script defer> de Docsify (el README tiene el ejemplo entero).

Salida real: en una página “Página sin site.js” con “Un párrafo con negrita.”, el botón descargó pagina-sin-site-js.typ con = Página sin site.js y Un párrafo con #strong[negrita].

Carga de plugins en site.js

Decision Clave nueva pluginModules en site.js Implicit

Docsify tiene que tener el plugin antes de arrancar. site.js importa los módulos de pluginModules en su propio módulo, antes del <script defer> de Docsify. Sin la clave, site.js hace lo mismo que antes.

Trade-offsite.js tiene una clave más. Para revertir: sacarla; el botón sigue entrando por window.$docsify.plugins, como sin site.js.

Discarded idea

Un <script type="module"> en la página que suma el plugin. Antes de site.js, Firefox ignora el import map; después, Docsify puede arrancar sin el plugin.

Botón de exportar

Decision exportButton recibe los engines, no la dirección de pandoc.wasm Implicit

Con los engines como argumento, el plugin no depende del navegador y acepta otro motor. El ticket pedía exportButton({ pandocWasmUrl }).

Trade-offEl sitio escribe exportButton({ engines: browserEngines({ pandocWasmUrl }) }). Para revertir: que exportButton acepte pandocWasmUrl y arme browserEngines adentro (un valor por defecto en transportes/docsify/export-button.js).

Engines del navegador

Para que el botón funcione en un sitio publicado (no bloquea el merge), alguien tiene que servir pandoc.wasm desde un host con CORS (por ejemplo, Caddy en el VPS). Pesa unos 56 MB: no entra a git, y jsDelivr no sirve archivos de más de 50 MB. Typst se baja de jsDelivr (@myriaddreamin/typst-all-in-one.ts) solo al pedir un PDF.

pandoc-wasm.js adapta pandoc.js, la interfaz JavaScript que viene con pandoc.wasm (licencia MIT, Tweag I/O y John MacFarlane). La función que arranca el runtime de Haskell es una copia sin cambios: nadie la revisó línea por línea.

Tests

  • site.js without pluginModules imports no extra module and keeps the theme's plugins first
  • site.js imports pluginModules in its module and puts their exports after the theme's plugins
  • exportButton draws one bar with .typ and .pdf buttons at the top of the page
  • .typ button downloads the page's Typst with its drawn Mermaid diagram
  • a failed export says why in the bar and frees the buttons
  • the plugin downloads template and filter from their addresses once
  • a page without drawn diagrams sends no Mermaid filter to Pandoc and does not download it
  • with browserEngines, components read the page with Docsify's window.marked
  • with real Pandoc and the real Lua filter, the drawn diagram replaces its Mermaid block
  • after moving to another page, the button exports that page
  • the motor's warnings reach the bar and the console
  • a template that failed to download is asked for again on the next click
  • captureMermaidSvgs turns HTML labels into centered SVG text Typst can draw
  • captureMermaidSvgs leaves the page untouched
  • inlineMermaidSvgs splices escaped SVGs and strips unmatched placeholders
  • inlineMermaidSvgs splices escaped SVGs and leaves a visible note for unmatched placeholders
  • inlineMermaidSvgs warns once per diagram it could not place
  • toTypst with the filter set and no diagrams keeps the Mermaid code instead of a placeholder
  • browserEngines downloads nothing until it is used
  • pandoc engine retries the download after a failure instead of remembering it
  • compilePdf loads typst once from the default address and returns its bytes
  • without marked and before Docsify loads, components fail saying which parser is missing
  • pandoc runs one conversion at a time, because pandoc.wasm shares one virtual folder
  • a pandoc.wasm run that prints only an error becomes an error with Pandoc's message
Note

En export-button.test.mjs, el test “a page without drawn diagrams exports its Mermaid blocks as code, without the filter” no mira el Typst que sale: espera que Pandoc no reciba el filtro Mermaid y que el botón no descargue el archivo .lua.
